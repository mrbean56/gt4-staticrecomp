# 2026-11-24

## GT4.VOL writer: byte-identical region (A2)

`scripts/gt4_volume_write.py` copies the GT4.VOL region from the pinned USA v2.00 image: prefix, catalogue
and stored entries, with an optional payload replacement at the entry's recorded stored size. With no
replacement the 2,459,502,592-byte region is reproduced byte for byte
(SHA-256 `49f1a67a75542f93b0ffcedd7ef4d83149b8d2165186ee96fd527980d3688e1c`). A change that needed a
different stored size was refused because the catalogue pages were not re-encodable yet. 10 synthetic
controls plus 3 real-disc ones.

## GT4.VOL writer: re-encoded catalogue and a resized replacement (TASK-216 A3)

The catalogue is now written from its decoded pages: the 64-byte header with the new stored size, the
XOR-encoded page offset table, and each page's header, entry table, keys and metadata. Byte identity of the
ToC is not claimed; self-consistency is: re-encoding all 407 shipped pages and parsing them back anywhere
returns the same 18,352 paths, offsets, kinds and sizes, through both this decoder and `gt4_volume.py`.

The page encoder reproduces a decoded page byte for byte from structure plus the bytes it must not invent: a
page's unused space is stale (not zero-filled) and its four trailer bytes (a data watermark on leaf pages, a
page number of Unknown meaning on index pages) are carried verbatim. Index keys, links and children are
untouched because routing is not implemented. The catalogue keeps its allocated 179 pages / 366,592 bytes
and the volume keeps its extent, so `data_start` (17,850,368) never moves; a change that would need either
to grow is refused instead of guessed.

Evidence run: `specdb/GT4_US2560/GENERIC_CAR.dbt` shipped 11,743 stored / 17,960 decoded; written back
uncompressed by `gt4_specdb.write_table` it is 23,120 bytes, and the writer's re-framing happens to be
smaller (8,984 stored), so no other entry's offset moved. In the rebuilt image all 18,352 paths enumerate,
the other 18,351 entries carry identical stored bytes (18,338 also compared decoded; 13 are larger than the
16 MiB decoded cap), the replaced entry decodes to exactly the built table, and `parse_table` reads 722
rows of 24 bytes with row 59 `b00a00002400000078320000d107030d0d00000000000000`. Rebuilt image:
5,314,478,080 bytes, SHA-256 `e8597dcf8f261354fcd0de39024d411472d7e2556d934eb11941ee25a89a272a`.

Two limits are named rather than hidden: the catalogue allocation cannot grow, and an entry's storage kind
and metadata length cannot change. Both would need a re-layout this milestone does not implement.

Whether the game boots and loads a rebuilt volume whose catalogue stored sizes differ from the shipped ones
is **Unknown** until the owner's in-game test. The image waits at `/tmp/opencode/gt4-rebuilt.iso` (a symlink
to `/home/mrbean/opencode/gt4/gt4-rebuilt.iso`, because `/tmp` had only 3.1 GB free on the 24 GB tmpfs).

## Larger field: the field size is a data byte (TASK-219)

Found the field size. A `RACE` SpecDB row is 151 bytes and its byte at 0x3E is `MaxEntries` (PDTools' mapping
between the unnamed byte at 0x3C and `StartType` at 0x40): 6 in 537 of 709 races, 2 in 86, 1 in 85, 4 in one. The
opponent pool `RACES/<row id>` is `[u32 count][u32 0]` plus 16-byte candidate entries (counts 0..29), and 196 of the
537 six-car races ship fewer than six candidates — one in 82 of them — so the engine's own data proves it repeats
candidates to fill a field instead of taking the pool size as the grid.

The load path reads that byte and grows: `RaceInformation__virtual_00` (0x3BB490) does
`count@+0x118 = max(count@+0x118, row[0x3E])`, and three information constructors start the counter at 6
(`RaceSinglePlayerInformation`, `RaceGTmodeInformation`, `RaceChampionshipInformation`). Calling `+0x118` the working
capacity is a Hypothesis; the arrays behind it are not proven to be sized from it.

`scripts/gt4_field_size.py --inspect` reports the histogram and the pools; without `--inspect` it copies the pinned
image, raises every six-car row to the requested size, re-serializes `RACE.dbt` and stores it through the volume
writer. Nine tests, three of them needing the disc or a built image. Built `gt4-field24.iso` (5,314,478,080 bytes,
SHA-256 `60e7ca91…`): 18,352 paths, 18,351 entries byte-identical at unmoved offsets, only `RACE.dbt` changed
(112,747 decoded / 8,997 stored, 537 rows at 24), bytes outside `GT4.VOL` identical before and after. Whether it boots
is Unknown; it rides the same uncompressed-table path as the earlier rebuilt image.

## SpecDB: all 79 tables, and what a car is (TASK-216)

The reader refused four shipped table shapes: `ARCADEINFO_TUNED` (0 rows, a dictionary header and a block header
only), and `DISPLACEMENT`, `WHEEL`, `WING`, which carry a one-code dictionary whose shipped 512-byte prefix table
does not describe that code (`00 01 00 ff` repeating). The prefix table is now advisory: when it does not validate,
decoding walks the code list from the shortest length. Zero-key label tables were refused too. After that all 79
tables parse and round-trip, and `write_labels` reproduces all 79 label tables byte for byte.

Then the label map. Every per-car row names the car in its label, so a car is a closed set: 95 rows in 44 tables for
`ka_01`, the same 95/44 for `m3_04`. Twenty identity rows (`GENERIC_CAR`, `CAR_NAME_*` ×9, `CAR_VARIATION_*` ×9,
`ARCADEINFO_NORMAL`), 67 rows in 21 two-letter families (`ch_`, `en_`, `ge_`, `ft_`, `rt_`, `su_`, `br_`, `cl_`,
`fw_`, `ls_`, `mu_`, `nt_`, `lw_`, `eb_`, `co_`, `bc_`, `rm_`, `no_`, `pp_`, `tk_`), and 8 class/event rows in
three tables (`DEFAULT_PARAM`, `DEFAULT_PARTS`, `ENEMY_CARS`). Row ids ascend in every row table — the game
binary-searches them — and the label tables are in shipped car order, not sorted.

`scripts/gt4_car_map.py` reports a code's set; `scripts/gt4_car_clone.py` plans and writes a clone of its 87
car-owned rows under a new code (41 tables), reusing the donor's strings so the first experiment proves the
mechanism before any string work. Images: `gt4-field24.iso` (fields, TASK-219) and `gt4-clone-xa99.iso` (a second
Ford Ka under code `xa_99`). Whether either boots is still Unknown; both ride the uncompressed-table path.
