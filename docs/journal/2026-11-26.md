## Course race data (.ad) decoded

- All 110 `.ad` files are the same container with a 32-entry slot table; 93 carry `ADLN` at slot 1 and decode into
  eight polylines. Header: magic, two reserved zeros, declared length, a third zero, count 8, table at 0x30, a fourth
  zero; then a table of eight offsets, then per line a 0x40-byte entry header (record count, rest zero) and that many
  0x40-byte records. The entry chain closes exactly on the declared length in all 93 files.
- Record: position at +0x04/+0x08 in the course's world units, a tangent heading at +0x24. The heading sits ~90
  degrees off `atan2(dz, dx)`, matches with a central-difference tangent to a median 6.5 degrees at the shipped ~130 m
  spacing, so it is a road heading rather than an exact tangent.
- Line roles (High confidence): 1/2 road edges (~5 m apart), 6 a second full-length line, 3 a third of different
  density, 4 a short near-straight line across the start area, 7 sparse and often absent, 5 empty everywhere.
- The 17 others (`ss_*` photo spots, `gymkhana_spiral_r`/`gymkhana_spral`, `testcourse_100m`) start with a
  pointer-like form (values such as `0xFFFEADF0`) and are kept verbatim; `read_lines` refuses them by magic.
- `CRSS` is not the start grid: its counts are never 6 and forward/reverse twins are byte-identical. Its records are
  world-space points (first pair on the racing line, the rest 40-190 m off and 5-36 m up); a per-region reference set
  is the working hypothesis.
- `scripts/gt4_course.py` generalised to the 32/64-entry tables; 176 GT4 tests pass.

## Course geometry is the car model form; model uploads decoded

- The shipped car model probe (`gt4_model_probe.probe_mdls`) validates **all 892 `MDLS` sections** across the 110
  courses: 67,565 models, 74,390 shapes. So a course's geometry is the same serialized model form as a car's, and
  TASK-217 and TASK-218 share one reader. `gt4_course.model_sections()` and `probe_models(section)` expose it, with a

- `scripts/gt4_model_stream.py` (7 controls) frames a descriptor packet and lists its VIF uploads. Every packet of
  `car/menu/fdeu0006` (154) ends exactly on its declared quadword; the float family decodes: 3x32-bit positions at
  VU 0xC000, 2x32-bit texture coordinates at 0xC040, 3x32-bit unit normals at 0xC080 (4,808 checked, all within

## The CARS record and the catalogue insert

- The record is `u32 count, u32 0` and 16-byte `(row id, table id, letter, 0)` entries. The Ka's 73 match its own
  `.idi` rows one for one; six are default rows shared between cars, so a clone keeps the donor's id for those.
  `scripts/gt4_car_index.py` (7 tests, real-disc included) reads it, writes it and maps a donor record through a
  clone plan.
- Inserting a file needed a real tree operation: the CARS leaf is full (42 entries, 19 free bytes). The writer packs
  the leaf, splits it, adds a child to the full index page (which splits too) and a separator to the root, and puts
  the payload after the last entry. Packing shrinks the catalogue, so the split fits the shipped page allocation. Two additions and every unchanged file are controlled.
- In game the cheap variant (rename the Eclipse's `CARS/…0435` to `…0436`, same slot) booted and ran the attract
  mode, then halted on `ra 0x0031C8A8` when leaving it: the missing Eclipse record is the likely cause (High
  confidence). The proper image `gt4-clone-record2.iso` (SHA-256 `f7b4f168…`) keeps all 804 records and inserts the
  clone's record through the split; `gt4_car_clone.py` now produces that image directly.

## Catalogue pages: links and trailers, and where a car code is resolved

- A page header is `kind, count, next_page, previous_page`. Leaves are doubly linked in key order inside
  one index page's range; index pages are linked among themselves, and the root lists the index pages. The four
  bytes before the entry table are a trailer: a leaf stores `(0, align4(data_end))` (all 401 shipped leaves), an
  index stores `(last page of its chain, 0)` (the 5 non-root index pages and the root, which stores the last index
  page 402). The insertion kept the trailers of every packed or split page stale — the split leaf still named the
  old data end and the split index page its old last leaf — because the offline reader never looked at them.
  `refresh_trailers` now rebuilds them from the links, and the insertion tests check every trailer.
- An index entry's key is the first key of the *next* child page, so a key is found by taking the first entry
  whose key is greater than it and, past the last entry, the page named by the trailer. The insertion broke that
  in two places: when an **index** page split, the separator passed to its parent was the upper half's first
  entry key (the first key of that child's *successor*) instead of `lower.entries[-1].key` (the first key of the
  upper half's own range), and `find_leaf_slot` chose a leaf by page-id order instead of walking the tree. A
  two-addition build made 42 `usedcar/` files unreachable through the tree while the linear reader still saw
  them; both are fixed, and a test now walks every record the way the game does.
- The roster files are Adhoc bytecode, not data tables: a maker's list is built by `PUSH_STRING` instructions with
  the source line first (`line, 0x1D, u16 length, code`), so the `u32` before a code is a line number, not an object
  id. `projects/boot/US_carlist.adc` holds `car_carlist` and `garage_carlist` (the same 240 codes twice), the table
  the engine resolves a code through. A code that appears only in a maker list is therefore not resolvable
  (High confidence), which is what the `ka_02` crash at `ra 0x0031C8A8` shows while the Ka's own relabelled row
  loads: the row and its CARS record are fine, the code is unknown to the engine.

## GT4.VOL can grow inside the disc image

The shipped volume has 446,424 B free after its last entry, while one course container is ~3.8 MB
compressed (`crs/deepforest`: 7,427,840 decoded). The disc image is 5,314,478,080 B; its filesystem
declares 2,697,330,688 B and every file ends by 2,676,342,784 B, so ~2.6 GB of the image belong to no
file and nothing reads them. `scripts/gt4_iso_grow.py` grows the volume forward into that tail and
moves the two ISO9660 fields that describe it — `/GT4.VOL;1`'s directory record length and the primary
volume descriptor's volume space size, both byte orders — takes the volume writer's replacements and
additions, zero-fills the grown tail and copies the image after the new volume end unchanged. The
writer gained `tail_zeros` for that filler.

The first attempt patched the primary volume descriptor's volume space size too, and the image booted
to a **black frame**: the runtime logs `layer 1 at 1317040` (the volume space in sectors) and under the
patched field it reported `145 files, layer 1 at 0`, so the descriptor field is how the runtime finds
the disc's second layer and must stay at its shipped value. The volume therefore grows only inside the
filesystem's own free tail: 2,697,330,688 - 2,676,342,784 = **20,987,904 B**, about five compressed
courses. Growing further needs the second layer understood.

Controls: `tests/python/test_gt4_iso_grow.py`, 8 tests on the real disc. The shipped record reads
back as 216,840,192 / 2,459,502,592; an 8 MiB grow keeps every shipped entry's offset, stored size
and size and leaves the volume space size untouched; an appended `crs/zz_probe` (a `crs/deepforest`
copy) decodes to its donor and reaches past the shipped end; the image tail after the new volume end is
byte-identical; the grown tail is zeros; zero growth and growth past the filesystem are refused.

The 16 MiB image raced (Confirmed in game). `gt4-grow-clone.iso` (file SHA-256 `cc5002b0…`) is the
racing 41-table clone grown by 16 MiB, with a `crs/deepforest` copy appended as `crs/zz_probe` ahead of
the clone's `CARS` record, which lands at 2,462,928,896 — 3,426,304 B past the shipped volume end. The
Ford page reads **"Ford Ka '01 Clone"** (frame 15,500), the Tsukuba entry list carries it at position 6
(frame 19,500) and the race starts with a live HUD (frame 20,500). Both screens take the name from the
`CARS` record, so the game reads catalogue entries stored past the shipped extent.
