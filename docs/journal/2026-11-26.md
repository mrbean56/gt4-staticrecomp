## The images in game: writer form, then the field data

Ran the port's candidate images on Bilboquet (Windows 11, RTX 3070 Ti) with the 1.3.0-rc16 game binary, the owner's
disc passed with `--disc` and a copy of the launcher's memory card. Arcade, Single Race, Nürburgring Nordschleife,
Ford Ka `01, the same click path every time.

- Shipped disc: six-car entry list, camera hook, race, no halt. Baseline.
- `gt4-rebuilt.iso`: boots to the menus, but its only change (`GENERIC_CAR.dbt` re-serialized in the uncompressed
  writer layout) is misread — the car screen prints `Type:--` and 90 HP at 499.5 rpm and refuses the car.
- `gt4-field24.iso`: race loaded, camera hook at vblank 41,033, then `[ee] halted: missing code at 0x00000000
  (ra 0x003FD354)`. The site is `lw v0,4(v1); jalr v0` after `v1 = *(obj+8)+0x58`: a virtual call through a null
  slot.
- `gt4-race-control.iso` (shipped values, same uncompressed layout): halted the same way at its own race start. So
  the halt was the writer layout, not the 24-car value — and a boot check alone proves nothing.

Fix: `gt4_specdb.write_table(..., compressed=True)` writes the shipped dictionary form (256 uniform eight-bit codes,
one raw-row stream per row, a block copy for rows longer than 254 bytes, `ALLOW_ENTRY`'s 480). All 79 tables
round-trip through it; the field and clone tools use it.

- `gt4-race-control2.iso` (dictionary form, shipped values): six cars, race clean.
- `gt4-field24b.iso` (dictionary form, 537 rows at 24): six cars, race clean.
- `gt4-field24c.iso` (also 469 pools cycled to 23 candidates): still six cars. **Arcade Single Race does not take its
  field from `RACE.MaxEntries` or the pool**; its six is the code default at `+0x118` in the race-information
  constructors (0x3D5AE0). The data half therefore governs GT Mode event rows (untested, needs a GT Mode save), and
  the owner's 24-car request needs the code half.

## Course race data (.ad) decoded

- All 110 `.ad` files are the same container with a 32-entry slot table; 93 carry `ADLN` at slot 1 and decode into
  eight polylines. Header: magic, two reserved zeros, declared length, a third zero, count 8, table at 0x30, a fourth
  zero; then a table of eight offsets, then per line a 0x40-byte entry header (record count, rest zero) and that many
  0x40-byte records. The entry chain closes exactly on the declared length in all 93 files.
- Record: position at +0x04/+0x08 in the course's world units, a tangent heading at +0x24. The heading sits ~90
  degrees off `atan2(dz, dx)`, matches with a central-difference tangent to a median 6.5 degrees at the shipped ~130 m
  spacing, so it is a road heading rather than an exact tangent.
- Line roles (High confidence): 1/2 road edges (~5 m apart), 6 a second full-length line, 3 a third of different
  density, 4 a short near-straight line across the start area, 7 sparse and often absent, 5 empty everywhere.
- The 17 others (`ss_*` photo spots, `gymkhana_spiral_r`/`gymkhana_spral`, `testcourse_100m`) start with a
  pointer-like form (values such as `0xFFFEADF0`) and are kept verbatim; `read_lines` refuses them by magic.
- `CRSS` is not the start grid: its counts are never 6 and forward/reverse twins are byte-identical. Its records are
  world-space points (first pair on the racing line, the rest 40-190 m off and 5-36 m up); a per-region reference set
  is the working hypothesis.
- `scripts/gt4_course.py` generalised to the 32/64-entry tables; 176 GT4 tests pass.
